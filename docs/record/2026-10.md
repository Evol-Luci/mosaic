## The `[script]` SIGSEGV

- ~~**The `[script]` SIGSEGV**~~ — **ROOT-CAUSED AND FIXED 2026-10-03. It was
  never a flake, and the cause was written in our own comment.**
  `ensure_interpreter` noted that after init "the calling (main) thread holds
  the GIL ... no explicit GIL handoff" — so whoever won the `std::call_once`
  race kept the GIL for the process. The threaded script test passed alone
  because the `ScriptWorker` thread won and held it; it died after any other
  engine had been created on the main thread, because the worker then called
  `PyDict_New()` with no GIL. `ctest` never saw it because
  `catch_discover_tests` gives every `TEST_CASE` its own process, so the worker
  was always first — **the gate was green and blind at the same time.**
  Fixed by making the invariant real: no thread owns the GIL implicitly, and
  every entry into CPython acquires. Four things that were not obvious going
  in, each of which cost a failing-gate iteration: `globals_` had to become a
  `std::optional<py::dict>` in both engines, because a `py::dict` *member* is
  built before the constructor body and destroyed after the destructor body,
  leaving no scope in which to guard `PyDict_New`; `restricted_builtins`'
  function-local static `ProxyClasses` had to start leaking, because
  `__cxa_atexit` destroys it with no GIL and `dec_ref` aborts -- and that abort is a
  *debug* symptom only (`PYBIND11_ASSERT_GIL_HELD_INCREF_DECREF` is defined when
  `NDEBUG` is unset), so in a Release build the same path is a silent unguarded
  `Py_XDECREF`: the leak is **more** necessary there, not less; `trace_fn_` had
  to be emptied inside the guarded destructor, since a `py::` member outlives
  the body; and every direct pybind11 user outside the engines — the docs
  generator and four test files that build their own `py::dict` — had to
  acquire too. Evidence: `[script]` in one process is 5/5 clean where it was
  RC=139 every time, the whole binary now runs in a single process (1081
  cases, 31577 assertions) which the crash made impossible, and removing the
  release makes the new tests **deadlock** rather than crash.

## `PhysicsSystem::raycast is callable from another thread while update runs` is flaky on CI, and the flakiness is in the test's design.

- ~~**`PhysicsSystem::raycast is callable from another thread while update runs` is
  flaky on CI, and the flakiness is in the test's design.**~~ — **FIXED 2026-10-09**,
  in the same PR that recorded it. The case ran 200 main-thread ticks, set `stop`,
  joined the reader thread, and only *then* asserted `REQUIRE(hits.load() > 0)`.
  Nothing synchronised the two, so on a **2-core** GitHub runner with the main thread
  busy stepping box3d the reader could be starved for the entire run and `hits` stayed
  0 — failing a test whose actual claims (no deadlock, no crash, the ray hits) had all
  been met. Observed failing 2026-10-09 on a **docs-only** PR that changed no code, and
  **not reproducible on a 20-core machine in 35 runs**, including under deliberate CPU
  contention — which is the whole story: the reader always gets a core here and may get
  none there. **The fix removes the dependency on the scheduler rather than widening a
  tolerance:** the main thread now waits (bounded, 5s, uncontended so it completes in
  microseconds) for the reader to land its first hit *before* the tick loop, so
  `hits > 0` is established deterministically; the concurrent phase that follows asserts
  nothing a scheduler can zero out — reaching the join without a deadlock or crash *is*
  the claim; and the ray's geometry is re-asserted afterwards **from the main thread**,
  which cannot be starved. The 5s ceiling exists so a genuine failure reports instead of
  hanging, and its message distinguishes "the reader was never scheduled" from "raycast
  from a non-main thread returns no hit".

## `execution.jobs` in the `debug` test preset (local `ctest -j`)

- ~~**`execution.jobs` in the `debug` test preset (local `ctest -j`).**~~ — **SHIPPED
  2026-10-24.** `CMakePresets.json`'s `debug` test preset now carries `"execution": { "jobs": 8 }`,
  so a bare `ctest --preset debug` runs parallel locally. CI is unaffected: its step passes
  `-j"$(nproc)"` explicitly, and an explicit flag overrides the preset field.

  **The decision was the human's and was delegated back with the measurements in hand.** The
  backlog had this as *decision-gated* ("a human's yes/no") because it changes every
  developer's default on machines of unknown memory. Asked, the human declined to pick blind
  and delegated the call. Measured instead (nproc=20, suite 1462, machine otherwise idle,
  3 runs per point, median):

  | `-j` | median wall | speedup |
  |---|---|---|
  | 1 | 26.44 s | 1.0x |
  | 2 | 13.42 s | 2.0x |
  | 4 | 6.99 s | 3.8x |
  | 6 | 5.05 s | 5.2x |
  | 8 | 3.92 s | 6.7x |
  | 12 | 3.28 s | 8.1x |
  | 20 | 2.93 s | 9.0x |

  **Why 8 and not `nproc`:** `execution.jobs` takes a literal integer -- there is no `nproc`
  expansion in a CTest preset -- so "nproc-wide" would mean hard-coding one machine's core
  count into a file every machine reads. That ruled out the maximum on portability grounds

**Shipped: a stdlib-only PCH on four targets.** One `MOSAIC_PCH_HEADERS` list in the

`<utility>`, `<optional>`, `<functional>`, `<unordered_map>`, `<array>`, `<cstddef>`,
`<string_view>`, `<chrono>`, `<stdexcept>`. `<fstream>`/`<sstream>`/`<iostream>` were
excluded: 22, 15 and 0 users is too few to justify making all 180 TUs load them.

`touch foundation/core/entity_id.hpp && cmake --build --preset debug -j20`, 180 TUs
both times. BEFORE 89.6 / 90.4 / 88.9 s; AFTER 80.4 / 80.0 / 79.6 s. Both spreads are
under 1% and the ranges do not overlap (worst AFTER 80.4 s beats best BEFORE 88.9 s),
so three runs each is enough and no statistics are needed.

**The measurement trap, recorded because it would have inflated the result.** The
baseline in the backlog was 83.2 s over 171 TUs, measured 2026-10-24 earlier. Comparing
the new 80.0 s against *that* gives 3.8%, and it would be wrong: the suite has gained
tests since, so the rebuild is now 180 TUs, not 171. Those two numbers describe
different amounts of work. The BEFORE was therefore **re-measured on the same tree, in
the same build directory, minutes before the AFTER** -- 89.6 s, not 83.2 s. Do not
quote 83.2 -> 80.0. The same reason is why the AFTER was not measured in the delegate's

**Two decisions, both recorded with their reasons.**

*Stdlib-only, no project headers.* This was settled before delegating, because the
tempting move is wrong in a way that is easy to miss: putting `entity_id.hpp` in the PCH
would be invalidated by exactly the edit the gate measures, forcing a PCH rebuild *and
then* all 180 TUs -- strictly worse than no PCH at all. A comment at the list says so,
because someone will try to add a project header there later.

*`PRIVATE`, not `PUBLIC`.* `PUBLIC` propagates the PCH to every consumer and silently
changes what their TUs see. The PCH is a build optimisation for these four targets, not
part of their interface.

**Unity builds were declined, not forgotten.** 10.7% was bought with a 6-line,
fully reversible CMake change. Unity builds would pay for the next increment in ODR and
internal-linkage semantics, and in error messages that point at files the author did not
touch. The trigger for revisiting is in the backlog.

**The risk, and the ruling on the guard.** A PCH's real hazard is include hygiene
drifting: a new file that omits `<vector>` compiles anyway, and breaks only for whoever
builds without the PCH. That was verified *not* to be true at ship time, as a negative
control rather than an assumption -- `cmake -DCMAKE_DISABLE_PRECOMPILE_HEADERS=ON` built
the whole repo with 0 errors in 97.6 s, which also independently confirms the gain (97.6 s
no-PCH vs 84.5 s full build with it). The delegate was explicitly forbidden from removing
any existing `#include`, for the same reason.

**The ruling on the standing guard was made twice, and CI overturned the first one.**
Initially it was declined on measured cost: a second full build against a job that takes
~1m42s in total, to protect a latent failure that only bites someone who disables the PCH.
That reasoning was sound and the conclusion was still wrong, because it assumed the only
way to get the guard was to *add* a build.

**What CI actually showed, and why the PCH is now off in CI.** The first CI run with the
PCH passed, but took **6m49s against the usual ~1m38s**. The cause was in the ccache stats,
not the build log:

| Run | Cacheable calls | Uncacheable | Job time |
|---|---|---|---|
| #294, pre-PCH | 452 / 452 (100%) | 0 | 1m38s |
| #295, PCH on | 213 / 456 (46.7%) | **243 / 456 (53.3%)** | 6m49s |

ccache cannot cache a compilation that consumes a precompiled header without sloppiness
settings, so 243 calls became uncacheable *by nature*. This was **not** a cold-cache
one-off, and the numbers rule that out rather than argue it: the cache restored fine
(315 MB on the restore key) and all 213 still-cacheable calls hit at 100%. So the trade as
first shipped was 10.7% off a local rebuild in exchange for ~5 extra CI minutes on every PR,
permanently -- a bad trade, and the opposite of the standing priority that CI time is a lever.

ever wanted and restores 452/452 cacheable. **And the include-hygiene guard that was
declined on cost is now free**, because the no-PCH build it asked for is the build CI
already performs on every PR. The consequence to accept knowingly: a missing `#include` can
now compile locally and fail in CI. That is the right direction for the failure to point.

**The lesson, stated plainly because it nearly shipped:** the local gate (an edit-one-header
rebuild) was the gate the row asked for, it was measured correctly, and it was still not
sufficient to justify the change. A build-system change has a second cost centre that the
local measurement cannot see, and the probe that found it was not the gate -- it was
comparing one CI run's ccache statistics against the previous PR's.

## A headless VkDevice for tests, slice 1: surfaceless device creation

**2026-10-24.** Raised by the user the same day ("we are limited from taking screenshots
because of this missing VkDevice, we should fix this soon"). This is slice 1 of 3, and it
is the foundation only: the project can now create a `VkDevice` inside a test, which it
could not do at any price before. It renders nothing.

**The reframe came first, and it is what made the work tractable.** Two blockers had been
conflated, and only one was ours. The sandbox genuinely cannot screenshot a GUI window
(`hyprctl`/`grim` are broken on this machine) -- environmental, unfixable. Nothing in the
test binary constructed a `VkDevice` -- entirely our own coupling. Fixing the second makes
the first *irrelevant* rather than fixing it, because an offscreen render plus a buffer
readback produces pixels through the driver with no compositor and no window in the
picture. **The goal was never a screenshot; it is a readback.** Framing it as "screenshot
the editor" is exactly what had made it look environmental and therefore hopeless.

**Feasibility was probed before anything was designed or delegated**, with a ~50-line
standalone program compiled and run on this machine. It reported: validation layer
present; instance created with NO surface extensions; 1 physical device; picked NVIDIA
GeForce RTX 3080, graphics family 0, `maxPushConstantsSize=256`; `vkCreateDevice` with no
swapchain extension SUCCESS; graphics queue obtained; **validation messages = 0**. So the
environment was never the obstacle, and the delegate was handed a working reference rather
than an open question. (The 256-byte push-constant limit also happens to satisfy the
production renderer's requirement exactly, which matters for slice 3.)

**What the blocker actually was, named to the function.** `VulkanRenderDevice`'s
constructor takes a `GLFWwindow*` and calls `glfwCreateWindowSurface` immediately;
`pick_physical_device` is surface-gated three ways (`device_supports_swapchain`,
`vkGetPhysicalDeviceSurfaceSupportKHR`, and surface-format/present-mode counts); and
`create_logical_device` always requests `VK_KHR_swapchain`. A headless path does not need
new rendering code -- it needs to stop *requiring* the swapchain.

**The probe discipline finding, which is the most useful thing in this entry.** The
delegate's test asserted `validation_message_count() == 0` and all 12 assertions passed.
Run again with the layer disabled (`VK_LOADER_LAYERS_DISABLE='*'`), **it still passed all
12**: with no layer there is no messenger, the callback never fires, and the count is
trivially zero. The case was reporting "validation clean" on a run where validation had
never executed -- a probe that could not fail. Fixed by asserting
`dev.validation_enabled()` *before* the count, in both scopes, with the measurement written
beside it so nobody deletes it as redundant.

**Both directions were then proved by mutation, and the first mutation was discarded for
being the wrong kind of red.** Removing `vkDestroyDevice` from `cleanup()` did turn the
test red -- with a SIGSEGV. That proves the test notices a crash, not that the validation
counter is load-bearing, so it was discarded and replaced with a mutation that produces a
real validation message without crashing: a deliberate zero-size `vkCreateBuffer` after
device creation. That failed on exactly the intended line, `validation_message_count() == 0`
expanding to `1 == 0`. So the counter fires on a genuine validation error, and the
`validation_enabled()` assertion fires when validation is absent. The case is now
load-bearing in both directions.

**The registration decision, which was forced rather than chosen.** The GPU case lives in a
new `mosaic_gpu_tests` target, built only under `-DMOSAIC_ENABLE_GPU_TESTS=ON`, default OFF.
The obvious alternative -- a Catch2 `SKIP` when no GPU is present -- would set `skipped=1`,
and `tools/ci/check_ctest_run.py`'s O2 check fails the build on any skip. That guard is
right and must not be loosened to accommodate this, because its whole purpose is that a
skip cannot masquerade as a pass. The default suite is therefore still **exactly 1462
tests, all passing** (verified in the same warm build directory, not taken from the
delegate's report), so `next-steps.md`'s State table and the #290 checker stay true.

**What this does NOT establish, stated plainly.** It is opt-in, so it protects nothing
automatically -- it is a manual verification tool until there is a GPU runner. And it
exercises a *parallel* surfaceless implementation, not the production constructor, because
`vulkan_render_device.cpp` was deliberately not touched: a slice whose gate cannot see
pixels has no business editing the renderer. Sharing the selection code between the two
paths is a follow-up for after slice 2 can observe a result.

## A headless VkDevice for tests, slice 2: offscreen readback and the first asserted pixel

**2026-10-24.** Slice 2 of 3. **This is the one that makes the gate able to see a pixel.**
Before it, nothing in 1462 tests had ever checked one.

**What it does.** `modules/render_vulkan/vulkan_headless_readback.{hpp,cpp}` takes an
existing `VulkanHeadlessDevice`, creates a 16x16 `VK_FORMAT_R8G8B8A8_UNORM` offscreen
image, clears it to RGBA (0x12,0x34,0x56,0x78), transitions
`UNDEFINED -> TRANSFER_DST_OPTIMAL -> TRANSFER_SRC_OPTIMAL`, copies the image into a
host-visible buffer, waits on a fence, maps it, and returns the pixels.
`tests/gpu/offscreen_readback_test.cpp` asserts **all 256** of them, twice in one process.
2587 assertions across the two GPU cases.

**A clear, not a drawn triangle, and that was a decision rather than a shortcut.** A clear
exercises the entire readback path -- image creation, memory type selection, layout
barriers, command submission, fence wait, image-to-buffer copy, host mapping and
non-coherent invalidation -- with none of the graphics-pipeline or SPIR-V surface. Had the
first asserted pixel been gated behind shader tooling it would not have landed in this
slice, and the readback machinery is the part everything later depends on. Drawing geometry
is slice 3.

**Design choices aimed specifically at making the assertion hard to satisfy by accident.**
The colour is (0x12,0x34,0x56,0x78) rather than black or white, so zeroed or uninitialised
memory cannot pass. All 256 pixels are checked rather than one, because a single sampled
pixel can match for the wrong reason while a whole buffer cannot. 16x16 is large enough
that a row-pitch error shows up. The test asserts the literal channel values
(`pixels[i].r == 0x12`) as well as the struct equality, so the expectation cannot drift with
the helper's input.

**Proved load-bearing by mutation, and the mutation was the decisive one.** The risk with a
readback helper is that it echoes its own input instead of reading the GPU, in which case
the test asserts nothing. Perturbing the clear's red channel by +1 in the implementation
turned the case red on exactly the right line -- `REQUIRE(pixels[i].r == 0x12)` expanding to

## A headless VkDevice for tests, slice 3 step 1: separating surface construction

**2026-10-24.** Slice 3 needs the readback pointed at the renderer's REAL draw paths,
which means `VulkanRenderDevice` has to be constructible without a window. This is step 1
of 2, and it is deliberately a **pure refactor that adds no capability**: it separates the
surface/swapchain-coupled construction so step 2 can add an offscreen variant. Splitting it
this way means that if something breaks, it is known which half broke it.

**The shortcut was probed and ruled out first.** `VK_EXT_headless_surface` would have let
the existing renderer work unchanged -- surface, swapchain, present and all -- with no
refactor whatsoever. It is not offered on this machine: the loader reports 25 instance
extensions under `DRIVER_ID_NVIDIA_PROPRIETARY` 610.57.04 and that is not among them. So the
refactor is necessary rather than merely the first idea. The probe also turned up that Mesa
**lavapipe** does implement it, which matters for a different reason and is captured in the
backlog: it would let these tests run on GPU-less CI runners, so slice 1's recorded trigger
of "a CI runner with a GPU" was too narrow.

**Scope, measured rather than assumed.** The constructor runs ~35 steps and only four areas
are surface-coupled: `glfwCreateWindowSurface`; `pick_physical_device`'s present-support
query, `device_supports_swapchain` and surface-format/present-mode checks;
`create_logical_device`'s `VK_KHR_swapchain` request; and the
`create_swapchain`/`create_image_views`/`create_framebuffers`/`extent_` group. Every render
pass, pipeline, descriptor and shadow/HDR/bloom resource needs only a colour format and an
extent. Nothing else was touched. `create_vulkan_render_device(GLFWwindow*)` keeps its exact
signature and wraps the argument, so no caller changed.

**THE GATE, and the finding that made it possible.** A standing assumption needed
correcting. `next-steps.md` said renderer behaviour is "checkable only by eye", and that is
true of PIXELS -- but it had been read as though nothing about the renderer were checkable.
The editor runs fine in this sandbox, and it runs under the validation layer with
**synchronisation validation enabled**. On unmodified `main` that produces exactly:

```
exit=124
[INFO] vulkan: synchronization validation ENABLED (MOSAIC_VK_SYNC_VALIDATION); expect it to be slower
[INFO] demo: baking environment IBL (a few seconds, once)
[INFO] demo: environment IBL ready
```

Three lines, zero VUIDs, zero ERROR, zero WARN, exit 124 (no natural exit, so the timeout is
the pass). That baseline was taken BEFORE the refactor and handed to the delegate as a
must-match. After the refactor the log is **byte-identical** -- verified with `diff`, in the
real checkout, not the worktree. For a change to 2700 lines of renderer code whose output no
test can see, that is the strongest evidence available, and it is considerably better than
"the suite is green". **This gate existed all along and was not being used.**

**The defect found by review, which green would never have shown.** The delegate's report
flagged, honestly, that it had kept the literal text
`glfwSetWindowUserPointer(window_, this);` intact so that a source-text contract test in
`bloom_backend_contract_test.cpp` would keep matching. The way it did so was to introduce a
**local variable named `window_`** -- trailing underscore, which in this codebase means a
member -- purely to satisfy a grep. Two things were wrong with that:

1. A local named like a member is actively misleading, especially now that the member of
   that name no longer exists.
2. More seriously, the test was using that line as its "end of the constructor" marker, and
   the line had just moved inside an `if (WindowTarget)` block. On a surfaceless path it
   will not exist at all, so in step 2 the marker would silently stop meaning what the test
   thinks it means -- while still passing.

Fixed on both counts: the local is gone (the call uses `wt->window` directly), and the test
is re-anchored on `VulkanRenderDevice(const VulkanRenderDevice&) = delete;`, which is unique
in the file, is genuinely the first thing after the constructor body, and does not depend on
which target was built. The reason is written into the test so the anchor is not "tidied"
back. **Re-anchoring preserved the test's teeth, and that was proved rather than assumed:**
removing `write_bloom_descriptors()` from the constructor still fails exactly 1 of the 44
`[bloom]` cases, with its intended message.

**The honest cost of splitting into two steps.** With only one variant in the
`std::variant`, every `holds_alternative<WindowTarget>` branch is currently always true, so
the not-taken branches are unexercised. That is the price of making step 1 provably
behaviour-preserving, and step 2 is what exercises them.

**Delegation note.** agy (Gemini 4 Argon, High). It did the refactor correctly, ran the
editor gate as instructed, and reported the contract-test contortion rather than hiding it
-- which is what made the defect findable. The report was accurate; the judgement that
shaping production code to satisfy a brittle grep was acceptable is what needed overruling.

## A headless VkDevice for tests, slice 3 step 2a: the real renderer, offscreen

Step 1 (#299) separated surface construction behind `RenderTarget`. Step 2a adds
the `OffscreenTarget` alternative, so the real ~6000-line `VulkanRenderDevice` —
the same class the editor uses, with its real pipelines and render passes — can
be built with no window, no surface and no swapchain, render, and be read back.

**Step 1 was more inert than "adds no capability" conveyed.** Reading the merged
code before specifying step 2 turned up that the offscreen path was not merely
unexercised, it was *not constructible*, for four independent reasons. Three I
predicted and the delegate confirmed; the fourth it found:

1. `create_swapchain()` was skipped, so `swapchain_format_` stayed
   `VK_FORMAT_UNDEFINED`, and `create_render_pass()` / `create_offscreen_render_pass()`
   use it as their colour format.
2. `create_render_pass()` set `finalLayout = PRESENT_SRC_KHR`, which is provided
   by `VK_KHR_swapchain` — not an enabled device extension offscreen.
3. `framebuffers_` was left empty while `ensure_swapchain_pass()` indexes
   `framebuffers_[image_index_]`.
4. **(found by the delegate)** `extent_` stayed `{0, 0}`, so `create_depth_resources()`
   and `create_hdr_target(extent_.width, extent_.height)` would create 0x0 images.

It also corrected one of my three: the hdr and bloom passes do *not* use
`swapchain_format_`, they hardcode `R16G16B16A16_SFLOAT`. Only the swapchain and
viewport passes were affected.

**The decision that made the slice worth doing:** the offscreen path *creates
swapchain-equivalent resources* rather than skipping. Same member names
(`images_`, `views_`, `framebuffers_`, `extent_`, `swapchain_format_`), so every
downstream pipeline, render pass and `draw_*` method runs unchanged. The
alternative — offscreen special-cases threaded through the draw paths — would
have produced a test exercising a *second* renderer, worthless as a gate on the
first. No `draw_*` method was touched. The only target-dependent change outside
construction, `begin_frame` and `end_frame` is `create_render_pass()`'s
finalLayout.

**Format: `B8G8R8A8_SRGB`, measured not guessed.** `choose_surface_format()`
prefers exactly that and also falls back to it, so it is what the window path
actually gets. A UNORM offscreen image would differ from the editor by a gamma
curve and the test would assert the wrong numbers confidently.

**Two images, not one,** matching `kFramesInFlight`: `render_finished_` is sized
from `images_.size()`, and ImGui's Vulkan backend requires MinImageCount >= 2.

### The defect in the test, and why "run it twice" was not enough

Slices 1 and 2 each ran their subject twice in one process, after a one-instance
fixture hid a shared-vertex-buffer alias from 1456 tests. So step 2a's spec
demanded two frames, reasoning that with `kFramesInFlight == 2` a second frame
uses the *other* image.

That spec was insufficient, and the delegate implemented it exactly as written:
**both frames cleared to the same colour.** A `read_pixels()` returning the stale
image, or an `end_frame()` rendering both frames into `images_[0]`, produces
byte-identical output and passes.

This was not argued, it was measured. With a one-line mutation making
`read_pixels()` always copy `images_[0]`, the same-colour test passed **all 35362
assertions**. With distinct colours per frame, the same mutation fails on the
intended line: `frame=1 pixel=0 r=137` where 225 was expected. The structure was
right and the data made it decorative.

The clear colours are now distinct per frame, and the expected bytes are computed
in the test from the float input through the sRGB transfer function and asserted
against a named constant (+/-1 per channel for rounding), so no value is
back-filled from observed output.

A second probe proved the validation assertion load-bearing too: adding
`COLOR_ATTACHMENT_WRITE` to a buffer barrier's `dstAccessMask` under
`PIPELINE_STAGE_HOST` fails `REQUIRE(validation_messages.empty())` with all 4096
pixel assertions still passing — a validation-only red, not a crash.

### Two defects fixed in review

- **`in_flight_` indexed by image, not by slot.** `read_pixels()` waited on
  `in_flight_[last_rendered_index_]`. `in_flight_` is `VkFence[kFramesInFlight]`,
  frame-slot indexed, and every other use indexes it with `frame_`. It was
  correct only because offscreen sets `image_index_ = frame_`, making the two
  numerically equal — a coincidence, not a reason, and an out-of-bounds read the
  moment the offscreen image count stops matching `kFramesInFlight`. Now tracks
  `last_rendered_frame_` explicitly.
- **A dead `if/else`** around `create_framebuffers()` with identical branches.

## A headless VkDevice for tests, slice 3 step 2b: the first asserted draw path

Step 2a made the real `VulkanRenderDevice` renderable with no window, but asserted
only a *cleared* frame — it could not see a single shader bug. Step 2b asserts
**where a real draw path puts its pixels**, which makes the negative-height
(Y-flip) viewport compensation machine-checkable for the first time in the project.

`tests/gpu/offscreen_ui_orientation_test.cpp` draws HUD quads through the real
`draw_ui` path on a 128x128 offscreen device and asserts the corners.

### A promise retracted before it was shipped

Three times across this slice the stated payoff was "the `screen_effect.vert`
Y-flip becomes machine-catchable". **That was wrong, and checking the types before
writing step 2b is what caught it.** `ScreenEffectParams` is exactly
`{ Vec3 tint; float tint_strength; float vignette; }` — a tint uniform across the
whole frame, and a vignette radially symmetric about the centre. Neither can
distinguish a vertically flipped `fragUV` from a correct one. **That shader's
missing compensation is not pixel-observable with today's parameters**, so no
readback test can catch it, and one claiming to would have been theatre.

The bug is real and still latent. The trigger for catching it is the first
*asymmetric* screen effect (a gradient, a scanline, a directional blur, an
off-centre vignette); at that point this test file is the template and the gate is
a few lines. Recorded rather than quietly dropped.

What IS catchable, and is now guarded, is `ui.vert`:
`gl_Position = vec4(nx * 2.0 - 1.0, 1.0 - ny * 2.0, 0.0, 1.0)`. That `1.0 - ny * 2.0`
is the compensation, it is the thing `screen_effect.vert` omits, and until now
nothing in 1462 tests touched it.

### The mutation, which is the whole evidence

A passing orientation test proves nothing by itself, so `ui.vert` was mutated:
`1.0 - ny * 2.0` -> `ny * 2.0 - 1.0`, removing the compensation. Run independently
twice (delegate, then re-run in review from a separate build dir), identical result:

```
frame 0 corners: top-left(8,8)=(99, 137, 188, 255) bottom-left(8,119)=(225, 188, 99, 255)
                 top-right(119,8)=(99, 137, 188, 255) bottom-right(119,119)=(99, 137, 188, 255)
```

`(99, 137, 188)` is the clear colour and `(225, 188, 99)` is the quad: the quad
moved from the top-left corner to the **bottom-left**, and the test failed on its
intended assertion. Restored, recompiled to SPIR-V, green again, `git status` clean.

### Design points

- **Asymmetric placement is the test.** The quad covers the top-left quadrant only
  (`rect = {0, 0, 0.25, 0.25}`). A centred or fullscreen quad cannot detect a
  Y-flip; it is the same reason a symmetric vignette cannot.
- **Both directions asserted:** the quad is where it should be AND the other three
  corners are still the clear colour. "It drew something somewhere" is not the claim.
- **Interior sample points** (8,8) / (8,119) / (119,8) / (119,119), not edges, so no
  off-by-one rasterisation argument is possible.
- Expected bytes computed through the sRGB transfer function from the float input,
  +/-1 per channel. One sample came back 241 against a computed 240 — within
  tolerance, and worth noting the tolerance is load-bearing, not decoration.
- Part two makes **two separate `draw_ui` calls** in one frame, two corners, both
  asserted. `draw_ui` uses push constants per quad with no per-frame staging buffer,
  so this is a composition check and is described as one — it is **not** an
  aliasing check, and the per-frame buffer aliasing class (`draw_particles`,
  `draw_ribbons`, `draw_world_text`) is still unasserted.
