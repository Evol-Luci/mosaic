# November 2026 — the record

Shipped-slice postmortems: what was decided, what was measured, which of the slice's own predictions were wrong. **New entries are appended directly at the end.** Shipped backlog entries moved out of `docs/project/deferred-work-backlog.md` also land here.

## The validation-observed flag gets a guard that can actually fail (2026-11-06)

🟡 row 11, the last of the findings that the review of #333 produced. Ten GPU tests assert
`validation_messages_are_observed()` before asserting the validation message list is empty;
that ordering is what stopped "no validation messages" from being true for free. The flag
those ten tests lean on was published by one line and checked by nothing:

```cpp
g_validation_observed.store(validation_layer_enabled_, std::memory_order_relaxed);
```

Measured 2026-10-30 on `401d027`: replacing that with `store(true, …)` left **12/12 GPU
tests passing with the layer present**, and with the backend's accidental "layer not
available" WARN out of the capture sink it left ten of them green having observed nothing.

### The premise was wrong, and in an instructive way

`vulkan_render_device.hpp` and the backlog row both named the fix: "the per-device accessor
shape that `VulkanHeadlessDevice::validation_enabled()` already has — the only check that
caught either fault". Building that would have produced a guard that still could not fail.

What saved those two `VulkanHeadlessDevice` cases was not per-device-ness. It was that they
read a **different variable**, set by a **second copy** of the layer-enablement logic that a
single-line edit in the other file does not reach. That is redundancy. Redundancy catches a
fault only until someone edits both copies, and it generalises to nothing: a per-device
accessor publishing a wrong value is exactly as unguarded as a global one.

The property that was actually missing: **a value is guarded when a test compares it against
a source that does not come from the code under test.** That reframing is what made the gate
reachable, and it is the transferable part of this slice.

### Why the obvious test cannot work

The gate the backlog set was "a wrong publish value turns a test red **with the layer
present**", and it was set that way deliberately, because the easy version is vacuous. When
the layer is enabled, `validation_layer_enabled_` is already `true`, so `store(true, …)`
publishes *the correct value by accident*. No assertion that only ever observes the enabled
case can distinguish the two lines — which is precisely why all ten consumers missed it, and
why they will keep missing it. They are not weak tests; they are blind to this fault by
construction.

### The two sources used instead

1. **`vkEnumerateInstanceLayerProperties`** — the loader's own answer to "is
   `VK_LAYER_KHRONOS_validation` installed", asked through the Vulkan API without passing
   through any Mosaic code. Catches a dropped store and `store(false, …)`.
2. **`VK_LOADER_LAYERS_DISABLE`** — the loader consults it at `vkCreateInstance` time, from
   the process environment. Setting it between two device creations flips the answer to "was
   the layer enabled" without editing code and without uninstalling the layer. This is the
   cell that meets the gate.

Both live in one case on purpose: cell 1 is cell 2's control, establishing that this device
reported `true` moments earlier, so a `false` in cell 2 is attributable to the environment
variable rather than to a machine that never had the layer. Split into two cases, each half
would pass in an environment where the flag was stuck at the value that half expects.

### What was measured, not predicted

| Run | Result |
|---|---|
| unmodified, layer present | **17/17 green** |
| `store(true, …)` — the fault | **1 of 17 red**, and it is the new guard; the other 16 green |
| `store(false, …)` | **11 of 17 red** — the ten consumers plus this case's cell 1 |
| unmodified, `VK_LOADER_LAYERS_DISABLE='*'` | **13 of 17 red, four pass** |

The `store(true, …)` row is the one that matters: before this slice it was 12/12 passing,
and the 16 still-green tests in that row are the direct evidence that no consumer of the
flag can police it.

`store(false, …)` turning 11 red confirms that direction was *already* covered, which is why
the defect only ever existed in the `true` direction — worth stating, because it means the
slice added exactly one cell of genuinely new coverage rather than two.

### A design question that answered itself

The first design assumed a child process would be needed, since the Vulkan loader might
cache layer enumeration for the lifetime of the process and ignore a later
`VK_LOADER_LAYERS_DISABLE`. The suite has no subprocess machinery, so that would have been
new infrastructure for one test. It turned out to be unnecessary: the loader re-reads the
variable per `vkCreateInstance`, so two devices in one process see different answers. The
test's structure proves this rather than assuming it — if the loader did cache, cell 2 would
fail, and the failure message says so explicitly instead of blaming the renderer.

### Predictions this slice got wrong

- The landmine entry's count. It has now mispredicted its own symptom **three times**: first
  "ALL 12 red at one assertion" (actually 10 + 2 elsewhere), then "12 of 16 red" with the
  four survivors unmentioned, and it would have been wrong again here. Re-measured on a real
  run: **13 of 17 red, four pass**, split 10/1/1/1. The entry now says the numbers are
  counted off an actual `VK_LOADER_LAYERS_DISABLE='*' ctest -L gpu` whenever they change, and
  never derived.
- The GPU suite count moved 16 → 17, so `next-steps.md`'s `Suite size` row changed. Both
  State rows were re-verified for real before their `Checked` dates moved — the check added
  in #331 exists because that is the step everyone skips.

### What is deliberately not in this slice

No change to the renderer's public API. The item was "guard a published value", and a guard
is a test. Moving the flag onto the device would be a larger change with no additional
guarantee, as above. The global remains "the most recently created device in this process",
which is fine for a single-device test process and is a separate concern if a second device
ever matters.
