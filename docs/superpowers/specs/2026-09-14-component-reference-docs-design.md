# Component Reference Docs Generator — Design

## Goal (Phase 5, Tool Ecosystem pillar — documentation tooling, part 2a of 2)

`mosaic docs`, a new CLI subcommand, walks every built-in component Mosaic
registers (via `ComponentReflection`) and generates
`docs/reference/components.md` — one reference page listing every component's
field names and default values. Part 1 (the docs hub nav generator) already
regenerates the hub's nav from whatever's actually in `docs/`; this slice adds
the reference content itself, and wires `docs/reference/` in as that
generator's already-anticipated 7th auto-group.

## Scope decision: components now, scripting globals later (2a vs 2b)

The original ask covered both engine components *and* the scripting globals
(`install_world_globals`'s ~16 gameplay globals, the `imgui_*` panel-drawing
set, the `MOSAIC_MENU_ITEMS`/`MOSAIC_PANELS`/`MOSAIC_IMPORTERS` plugin
conventions). Investigating both mechanisms found they're **not** equally
reflection-driven:

- **Components** are genuinely introspectable at runtime:
  `ComponentReflection::registered_names()` lists every registered type, and
  `ComponentReflection::inspect(world, entity, name, visitor)` walks a live
  instance's fields via the existing `FieldVisitor` interface (the same one
  Studio's Inspector panel already uses) — no new engine machinery needed.
- **Scripting globals** are plain C++ lambdas registered directly into a
  `py::dict` (`globals_["name"] = py::cpp_function(...)` in
  `modules/script_python/world_globals.cpp` and
  `modules/script_python_studio/studio_plugin_script_engine.cpp`) — pybind11
  doesn't expose their names/signatures/docstrings for introspection unless
  each registration is annotated with one (a real, separate, more invasive
  change touching ~30 individual call sites across 2 files, not something to
  take on as a side effect of this slice).

**Decision:** this slice covers components only (2a). Scripting-globals
reference docs are explicit future work (2b), gated on first adding pybind11
docstring annotations to `install_world_globals` and the `imgui_*` globals —
its own, separate spec once that prerequisite exists. `docs/design/scripting.md`
already covers the scripting surface in hand-written prose in the meantime.

## A real limitation in what's introspectable

`FieldVisitor`'s `field_readonly(name, display)` callback is used uniformly
for `bool`, every non-`float` arithmetic type, `EntityID`, and
`Handle<R>` fields — the callback signature carries a name and a pre-formatted
display string, not which of those underlying types triggered it. Reference
docs built on this can show a field's **name and default value**, but not a
precise type label for anything routed through `field_readonly` (e.g. a `bool`
field renders as `enabled: false`, not `enabled: bool = false`). Extending
`FieldVisitor` with more granular callbacks would fix this, but that interface
is shared with Studio's Inspector — a cross-cutting change out of scope here.
Accepted and documented, not solved, in this slice.

## Design

### `mosaic docs` — a new, argument-less CLI subcommand

Unlike `create`/`build`/`import`, this subcommand documents built-in *engine
types*, not anything project-specific — no positional project-directory
argument. `app/cli/options.hpp` gains `Command::Docs`; `app/cli/options.cpp`
wires `app.add_subcommand("docs", ...)` with no options at all.

### `app/docs/component_reference.hpp` — the testable core

```cpp
std::string generate_component_reference_markdown(
    const mosaic::engine::reflection::ComponentReflection& types);
```

Header-only (mirrors `app/project/project_io.hpp`'s split: a reusable core
function here, a thin CLI wrapper in `app/run/docs.cpp`). Internally:
constructs its own throwaway `World` + one entity; for each name in
`types.registered_names()` (already alphabetically sorted): `add_default` the
component, walk it with a local `FieldVisitor` implementation that renders
`- \`field_name\`: <default value>` lines (nested groups indented, via
`begin_group`/`end_group`), append a `## <ComponentName>` section, then
`remove_value` before moving to the next component — so no component's
transient throwaway state leaks into the next one's walk. Output opens with an
HTML-comment banner (`<!-- AUTO-GENERATED by \`mosaic docs\` -- do not edit by
hand -->`) and a short intro paragraph naming the type-label limitation above.

### `app/run/docs.cpp` — CLI glue

Mirrors `app/run/create.cpp`'s shape exactly: `register_builtin_components`,
call the core function, `fs::create_directories` + write to
`MOSAIC_DOCS_DIR/reference/components.md` — a new compile-time define in
`app/CMakeLists.txt`, mirroring the existing `MOSAIC_FONT_DIR`/
`MOSAIC_TEMPLATES_DIR` pattern (so the tool always writes to the right place
regardless of the process's CWD, same reasoning as those two).

### Wiring into the nav generator

`tools/docs/regenerate_nav.py`'s `GROUPS` gains a 7th entry:
`("reference", "reference", "alphabetical")` — exactly the follow-up its own
spec already named. `docs/index.html` gains a new `Reference` nav-group
(placed right after `Design`, before `Project & Legal`) with its own marker
pair, empty until the first real `mosaic docs` run populates it.

## Testing

- **`tests/unit/app/component_reference_test.cpp`** (new): register a handful
  of small, synthetic components with known field shapes (a bare `float`
  field, a `std::string` field, a `bool` field routed through
  `field_readonly`, a nested-group field) directly in the test — not the real
  28-component registry — and assert the exact rendered markdown for each
  shape. A separate integration-style case runs the function against the
  *real* `register_builtin_components` registry and asserts only structural
  properties (the banner is present, every one of the 28 real component names
  appears as a `## ` heading, output is non-empty) — a smoke test that won't
  need updating every time a real component's fields change.
- **`tests/unit/app/options_test.cpp`** (extended): `mosaic docs` parses into
  `Command::Docs` with no further options required.

## Non-goals / follow-ups

- **Scripting-globals reference docs (2b)** — needs pybind11 docstring
  annotations added to `install_world_globals`/`imgui_*` first; its own,
  later spec.
- **Precise field type labels** — would need extending the shared
  `FieldVisitor` interface; deferred, documented above.
- **Per-component markdown files** (vs. one combined page) — a single page
  was chosen deliberately: 28 components is small enough for one scannable
  page, and it means the nav generator only ever needs to track one file in
  the new `reference` group, not up to 28.
- **Wiring `mosaic docs` into CI or a pre-commit hook** — same accepted-gap
  shape as the nav generator's own manual-invocation trade-off.
