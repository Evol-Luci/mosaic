# Scripting Globals Reference Docs — Design

## Goal (Phase 5, Tool Ecosystem pillar — documentation tooling, part 2b of 2)

Part 2a ([Component Reference Docs Generator](2026-09-14-component-reference-docs-design.md))
deliberately deferred the scripting-globals half of documentation tooling,
because — unlike components — the ~26 scripting globals (`install_world_globals`'s
16 gameplay/plugin globals, plus the 10 `imgui_*` Studio-panel globals) are
plain C++ lambdas registered directly into a `py::dict`, with no reflection
mechanism exposing their names/signatures. 2a's spec named the prerequisite:
add pybind11 docstring annotations to those registrations first. This slice
does that, then extends `mosaic docs` to render a second reference page,
`docs/reference/scripting-globals.md`, by introspecting a throwaway globals
dict rather than hand-transcribing signatures — so the page can't drift from
the real registrations the way hand-written prose could.

## Docstrings at the source

Every `py::cpp_function(...)` in `modules/script_python/world_globals.cpp`
gains a docstring argument (pybind11's third positional arg to
`cpp_function`, after the callable and before/alongside `py::arg(...)`).
pybind11 auto-prepends a generated signature line to `__doc__` (e.g.
`get_component(arg0: int, arg1: str) -> object`), so docstrings only need to
describe *behavior*, not repeat parameter types — one short sentence each,
matching this repo's existing comment-density convention. No behavior change;
these are additive constructor arguments.

## `install_imgui_globals` extraction

The 10 `imgui_*` globals are currently registered inside
`StudioPluginScriptEngine::install_imgui_globals()`, a private method of an
anonymous-namespace class in `studio_plugin_script_engine.cpp` — there is no
reusable entry point to build them into a dict outside a real engine
instance, the way `install_world_globals` already is a free function.

Extracted to a new free function in a new
`modules/script_python_studio/imgui_globals.hpp`/`.cpp`:

```cpp
void install_imgui_globals(py::dict& globals,
                           std::function<void()> require_drawing,
                           int* child_depth);
```

`require_drawing` replaces the class's `this->require_drawing()` call (each
lambda calls the passed-in callback first, same semantics); `child_depth`
replaces direct access to `child_depth_`. `StudioPluginScriptEngine` calls it
with its real guard and `&child_depth_`; docs generation (below) calls it
with a no-op callback and a throwaway local `int`, and never invokes any of
the registered functions — only reads `__doc__` off them. Each `imgui_*`
registration gains a docstring the same way `world_globals.cpp`'s do.

## `app/docs/scripting_globals_reference.hpp`/`.cpp` — the new generator

Kept separate from `component_reference.hpp`, which stays header-only and
Python-free (mirrors 2a's own `app/project/project_io.hpp` split reasoning).
This generator needs pybind11/CPython, so it gets its own `.cpp`:

```cpp
std::string generate_scripting_globals_reference_markdown();
```

Internally: `mosaic::script::python::ensure_interpreter()`, then one
`py::dict`. Calls `install_world_globals(globals, &dummy_world, &dummy_types,
&dummy_stack)` with dummy `World**`/`ComponentReflection**`/`CommandStack**`
locals (each pointing at `nullptr`) — safe because introspection never calls
the registered functions, only reads their `.doc()`/`__doc__`, so the
pointers are never dereferenced. Then calls
`mosaic::script::python_studio::install_imgui_globals(globals, [](){}, &dummy_depth)`
into the *same* dict (names don't collide with the world globals).

For each of the 26 names, in two fixed, hand-ordered lists (not dict
iteration order, which pybind11/CPython doesn't guarantee): renders
`### name` + a fenced-code signature line (the first line of `__doc__`) + the
docstring body (the rest of `__doc__`, blank-line-separated per pybind11's
convention) under one of two `##` sections:

- `## World & Entity Globals` — the 16 `install_world_globals` names,
  available to gameplay `ScriptComponent` scripts, Studio menu-item/panel
  plugins, and asset importers alike.
- `## Studio Panel (\`imgui_*\`) Globals` — the 10 panel-drawing names,
  available only inside a `MOSAIC_PANELS` draw function.

A third, static section, `## Plugin Conventions`, is hand-written prose (not
introspected — there's no registration call these three dict-key conventions
route through): documents `MOSAIC_MENU_ITEMS`, `MOSAIC_PANELS`, and
`MOSAIC_IMPORTERS` at the level `docs/design/scripting.md`'s existing
"Studio plugins" section already does, condensed to a reference-page
paragraph each with a pointer back to that doc for the full narrative.

Output opens with the same
`<!-- AUTO-GENERATED by \`mosaic docs\` -- do not edit by hand -->` banner
`components.md` uses, so the nav generator's existing filename-fallback title
rule (documented in `docs/design/documentation-tooling.md`) applies to this
file identically — `Scripting Globals` shown in the nav via the same fallback
path `components.md` already exercises. This is expected, matching that
existing accepted case, not a new gap.

## `run_docs()` — CLI glue

`app/run/docs.cpp` calls both generators and writes both files under the
existing argument-less `mosaic docs` subcommand — one command, two output
files, mirroring how the docs-hub nav generator handles seven groups in one
run. No CLI changes. `mosaic_app` already privately links
`mosaic_script_python` and `mosaic_script_python_studio` (used today by
`run/editor.cpp`), so no new `app/CMakeLists.txt` link changes; the new
`.cpp` files (`scripting_globals_reference.cpp`, `imgui_globals.cpp`) are
added to `mosaic_app`'s and `mosaic_script_python_studio`'s source lists
respectively.

## Wiring into the nav generator

`docs/reference/` is already an auto-generated group (added by 2a); no
`tools/docs/regenerate_nav.py` changes are needed — the next run after this
lands picks up the new file automatically, alphabetically ordered alongside
`components.md`.

## Testing

- **`tests/unit/app/scripting_globals_reference_test.cpp`** (new): asserts
  the banner is present, all 16 world-global names and all 10 `imgui_*`
  names appear as `### ` headings under their respective `## ` sections, each
  has a non-empty docstring body (not just the auto-generated signature
  line), and the three plugin-convention names
  (`MOSAIC_MENU_ITEMS`/`MOSAIC_PANELS`/`MOSAIC_IMPORTERS`) appear under
  `## Plugin Conventions`. Structural assertions only (mirrors 2a's
  smoke-test case for the real component registry), not exact-string
  matching against every docstring's prose — so editing a docstring's wording
  later doesn't break this test.
- **`tests/unit/script_python_studio/imgui_globals_test.cpp`** (new): the
  extracted `install_imgui_globals` free function registers all 10 names into
  a fresh `py::dict`; a case with a no-op `require_drawing` callback confirms
  none of the 10 are invoked merely by installing them (no crash, no
  callback firing) — installing must stay side-effect-free, since docs
  generation relies on that.
- **Existing Studio-panel tests** (`studio_plugin_script_engine_test.cpp` or
  equivalent, wherever `imgui_*` click/error-isolation behavior is currently
  covered) are updated only if the extraction changes an include path or
  namespace — behavior itself is unchanged, same lambdas, same guard
  ordering, just relocated.

## Non-goals / follow-ups

- **Precise Python type checking beyond pybind11's own argument coercion** —
  out of scope; unchanged from today's behavior.
- **Docstrings for gameplay `ScriptComponent`'s own API surface beyond these
  26 globals** (e.g. component field names themselves) — that's what
  `components.md` (2a) already covers; no overlap intended.
- **A single merged reference page combining components and scripting
  globals** — two pages was chosen deliberately: different audiences
  (component authors vs. script/plugin authors), and it keeps each page's
  `mosaic docs` regeneration independent (touching one never rewrites the
  other's unrelated diff).
